Teaching Traffic Lights to Think: Multi-Agent RL on the Palapye A1 Corridor

Tsotlhe Seiphepi · June 2025 · 8 min read

Traffic congestion in growing African cities is not just an inconvenience. It wastes fuel, delays emergency vehicles, reduces productivity, and contributes to emissions. Palapye, a fast-developing town in central Botswana along the A1 corridor, has a triple-intersection network that sees significant daily traffic load. Traditional fixed-time signal controllers have no awareness of real-time conditions. They run the same cycle whether the road is empty or gridlocked.

This project explored a different approach: training a team of autonomous agents using Multi-Agent Deep Reinforcement Learning to control all three intersections simultaneously, learning from experience how to reduce congestion across the entire network rather than at any single junction.

Why Multi-Agent, and Why PPO

Single-agent RL approaches to traffic signal control treat each intersection independently. An agent controls one junction, optimising its own metrics without accounting for what happens downstream. If intersection A clears a queue rapidly, it may flood intersection B before B is ready. The intersections are coupled, so treating them independently produces suboptimal results at best and new bottlenecks at worst.

Multi-agent reinforcement learning lets multiple agents control multiple intersections while sharing information during training. The approach used here, MAPPO (Multi-Agent Proximal Policy Optimisation), combines the stability and sample efficiency of PPO with a cooperative multi-agent framework.

MAPPO is an extension of PPO to the multi-agent setting. Each agent maintains its own policy but is trained using a centralised value function that has access to the global state. At execution time, each agent acts using only its local observations, which makes the system deployable without a central communication hub.

The Architecture: CTDE

The system follows a Centralised Training, Decentralised Execution (CTDE) architecture. During training, a central critic observes the full state of the network — queue lengths, waiting times, and phase information at all three intersections simultaneously. This allows each agent's policy to be informed by what other agents are doing, enabling cooperative behaviour to emerge.

At deployment, each agent only sees its own local observations: the queue length on each approach, the current phase, and time elapsed in the current phase. No inter-agent communication is required at runtime. This is critical for real-world viability — the system does not depend on a reliable network link between junction controllers.

The three agents each control one intersection on the Palapye A1 triple-junction network, with the following local state space per agent:

  • Queue length on each approach lane
  • Current signal phase (one-hot encoded)
  • Time elapsed in the current phase
  • Waiting time for vehicles at the front of each queue

Simulation Environment: SUMO

All training and evaluation ran inside SUMO (Simulation of Urban MObility), an open-source microscopic traffic simulator. SUMO models individual vehicles, their interactions, and their responses to signal states. The Palapye triple-intersection network was built inside SUMO with realistic lane configurations and demand patterns.

The Python interface to SUMO, traci, allowed the RL agents to observe the simulation state at each time step and issue phase change commands. Each training episode simulated a period of traffic demand, and agents accumulated rewards based on the network-level performance metrics.

Curriculum Learning for Stable Training

Training a team of agents to coordinate from scratch on a complex multi-intersection environment is unstable. Agents initially produce random behaviour, which causes the simulated network to seize up completely. Sparse reward signals make it difficult for the agents to learn any useful policy before training diverges.

The solution was curriculum learning: starting with a simplified version of the problem and gradually increasing complexity as the agents improved. Early episodes used low traffic demand and gave agents larger reward signals for any reduction in queue lengths. As training progressed, demand increased, the reward shaping became more sparse, and the full complexity of coordinating all three intersections was introduced.

This staged approach produced significantly more stable learning curves and allowed the agents to build on basic signal timing intuitions before facing the full coordination challenge.

Reward Design

Each agent receives a reward signal based on a weighted combination of metrics at its intersection. The central critic aggregates these across all three agents to compute a global value estimate. The reward components were:

  • Queue length: negative reward proportional to total vehicles waiting
  • Waiting time: negative reward for vehicles with high accumulated delay
  • Throughput: positive reward for vehicles exiting the intersection
  • Pressure: negative reward for imbalance between incoming and outgoing flow

Balancing these components required iteration. Overweighting throughput alone caused agents to switch phases aggressively, which increased wear on the signal hardware and created uncomfortable stop-start patterns for drivers.

Training Results

The training dashboard above shows the agents improving over time across all tracked metrics. Reward climbs steadily through the curriculum phases, with a noticeable jump when curriculum difficulty increases and the agents successfully adapt rather than regress.

Compared to a fixed-time baseline controller, the trained MARL agents produced meaningful reductions in average queue length and vehicle waiting time across the network. The agents also demonstrated adaptive behaviour in response to demand fluctuations, holding green phases longer during high-demand periods and releasing phases quickly when queues were short.

What Did Not Work (and What It Taught Me)

The first several training runs diverged entirely. Agents learned to hold a single phase indefinitely, which drained queues on one approach while completely blocking all others. This is a classic failure mode in traffic RL and pointed to a reward shaping problem — the agents were finding local optima that scored well on one metric but were catastrophic globally.

Adding the pressure component to the reward function resolved this. Pressure penalises the difference between the number of vehicles arriving at an intersection and the number leaving, which forces agents to consider the downstream impact of their decisions.

The other major lesson was about the importance of the CTDE structure specifically. An early experiment with fully independent agents (no centralised critic) produced agents that learned reasonable individual policies but actively interfered with each other at the network level. Introducing the shared critic was the intervention that made coordination emerge.

Limitations and Where This Goes Next

The current work is simulation-only. SUMO is a high-fidelity simulator but it is still a model of the real world, not the real world itself. Real deployment would require integration with physical signal controllers, sensor infrastructure to feed real-time state observations, and extensive safety validation before any live testing.

The demand patterns used in training were based on estimates rather than measured traffic counts from Palapye. Getting real vehicle count data from the Botswana Road Transport Department would allow for much more realistic and useful training scenarios.

Extensions worth exploring include: incorporating pedestrian phases, handling incident scenarios where a lane is blocked, and extending the architecture to the full A1 corridor rather than just the triple-intersection section.
